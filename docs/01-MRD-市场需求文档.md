# 「猫吃了吗」MRD：市场需求文档

> 版本：v0.2 产品决策稿  
> 日期：2026-07-28  
> 说明：本文以当前用户访谈和产品实践为依据，不引用尚未验证的市场规模数字。

## 1. 文档目的

判断“挑食猫试吃记忆与补货决策”是否是一个值得继续投入的真实问题，并明确首批用户、核心价值和验证方式。

## 2. 市场背景

猫食品消费具有以下特征：

- 主食罐、零食罐、冻干、猫条等类型下，品牌、系列、肉源、质地和规格组合繁多；
- 海外罐头常通过代购、团购、暗号或临时低价渠道购买；
- 同一产品的购买链接与价格并不稳定；
- 猫的接受度具有明显个体差异，通用评分不能替代自家猫的历史反馈；
- 猫可能今天喜欢、过一段时间又不喜欢；
- 用户愿意尝新，但不愿承担复杂记录成本。

因此，用户真正缺少的不是“更多商品资料”，而是一套能够持续反映自家猫当前偏好的个人判断系统。

## 3. 目标市场

### 3.1 首要用户

高频尝新、家中有明显挑食猫、经常购买进口罐头或多品牌湿粮的猫主人。

典型特征：

- 手上同时有多款、甚至几乎不重样的罐头；
- 新品通常只少量购买，吃得好才复购；
- 会给新品 1–2 次机会，不会只凭第一次永久下结论；
- 记得明显不吃的产品，却容易忘记“吃过一半、似乎还行”的产品；
- 补货时才会寻找当期低价渠道，不依赖原购买链接；
- 愿意观察猫，但不愿长期维护表格或完整日记。

### 3.2 次级用户假设

- 需要为多只猫分别记录口味偏好的家庭；
- 正在排查肉源或质地偏好的猫主人；
- 需要与家人或代喂人共享喂食判断的人。

这些用户暂不进入首版开发范围，先验证单猫、单设备闭环。

## 4. 用户任务

### 核心任务

当我给猫尝试一款食物时，我希望用极低成本记住它的真实反应，以便未来决定是否继续尝试、长期回购或停止购买。

### 衍生任务

- 当我再次打开同一款时，不想重新拍照和填写信息；
- 当我第一次拍包装时，希望系统先识别常用字段，我只负责确认或修改；
- 当库存快吃完时，希望快速看到应该找哪些款；
- 当猫突然不爱吃以前喜欢的产品时，希望保留变化而不是覆盖历史；
- 当猫闻完就做埋屎动作时，希望明确标记，避免再次踩雷；
- 当一顿的整体食欲异常时，希望可以记录“无法判断”，而不是污染产品结论。

## 5. 现有替代方案

| 替代方案 | 优点 | 主要缺口 |
|---|---|---|
| 靠记忆 | 无操作成本 | 品牌与口味多后容易混淆；难以回忆中间态 |
| 电商购买记录 | 自动保留商品 | 渠道变化大；无法记录猫的反应；同款链接不稳定 |
| 备忘录/聊天记录 | 灵活 | 难检索、难形成补货结论、需要主动组织 |
| 表格/Notion | 可结构化 | 录入成本高；移动喂食场景不顺手；容易弃用 |
| 自动喂食机记录 | 自动记录克重 | 主要覆盖干粮；无法解释湿粮和加餐的行为反应 |
| 通用宠物 App | 功能多 | 往往偏健康、日程或社区，不聚焦“尝新—判断—补货” |

## 6. 核心机会

### 6.1 机会定义

把零散、容易遗忘的试吃经历，转化为补货时可以直接使用的个人判断。

### 6.2 产品价值

对用户：

- 少买明显不吃的；
- 不错过曾经表现不错、但名字记不住的；
- 不因一次异常就永久淘汰一款；
- 不需要维护复杂食谱或精确克重；
- 补货时直接获得小范围候选清单。

对产品：

- 反馈越多，个人判断越有价值；
- 记录以自家猫为中心，不容易被公共商品数据库替代；
- “偏好会变化”的时间序列是区别于普通收藏夹的关键。

## 7. 产品定位

### 定位语

给挑食猫主人的个人试吃档案：轻轻记一下，补货时少踩雷。

### 不是什么

- 不是罐头百科；
- 不是电商比价或带货平台；
- 不是兽医诊断工具；
- 不是营养配方管理器；
- 不是要求每天打卡的精细喂养日志；
- 不是固定购买链接收藏夹。

## 8. 为什么首版选择 H5 / PWA

- 不需要先完成应用商店或小程序上架，即可开始真实使用；
- 可通过“添加到主屏幕”保留接近 App 的启动入口；
- 拍照、相册、本地存储和离线缓存足以支持个人版闭环；
- 可使用独立邀请链接让 2–3 位测试者进入，后续再接匿名身份与云同步；
- 先验证真实使用频率和留存，稳定后再决定是否迁移微信小程序或独立 App。

## 9. MVP 市场验证目标

### 需要验证的关键假设

1. 用户是否真的会在同一款食物上留下多次反馈？
2. 五种行为反馈是否足够直观，是否会产生选择犹豫？
3. “滚动 90 天内 3 次正向反馈进入长期回购”是否符合实际判断习惯？
4. 补货清单是否会在真实购买前被打开？
5. 用户是否会因为记录成本过高而在一周后停止使用？
6. 真实包装照片是否比标准商品图更利于识别？
7. 包装识别能否明显降低首次建档的放弃率？

### 首轮建议样本

- 先由内部 3–5 位真实猫主人使用 2–4 周，验证建档、反馈和补货流程；
- 每位至少录入 5 款产品；
- 至少有 2 款产品被记录 2 次以上；
- 至少发生一次真实补货前查看。

滚动 90 天规则无法在 2–4 周内完成自然验证。首轮可用测试数据检查状态转换，真实有效性需继续观察至少 3 个月。

### 建议观察指标

| 指标 | 说明 |
|---|---|
| 建档完成率 | 开始拍照后成功加入试吃清单的比例 |
| 二次反馈率 | 已建档产品中，获得第 2 次反馈的比例 |
| 三次验证率 | 已建档产品中，完成 3 次有效反馈的比例 |
| 识别确认率 | 包装识别结果中，无需修改或只需少量修改即可保存的比例 |
| 单次反馈耗时 | 从进入反馈页到提交的时间 |
| 补货清单使用率 | 用户在补货周期内是否打开清单 |
| 30 日有效留存 | 30 天内是否再次记录或查看补货清单 |
| 主观记忆减负 | 用户是否认为“不用再努力记名字了” |

首版尚未接入埋点，这些指标可通过体验访谈和测试版本日志先行验证。

## 10. 风险

| 风险 | 影响 | 初步应对 |
|---|---|---|
| 用户不愿记录 | 产品无法积累价值 | 把反馈压缩为一次点击；避免必填长表单 |
| 同款识别困难 | 重复建档 | 搜索与人工确认兜底；包装识别优先提供同款提示 |
| 三次规则过于简单 | 推荐失真 | 只计算滚动 90 天内有效反馈，完整历史继续保留 |
| 猫的食欲受健康影响 | 错误归因给食物 | 提供“没法判断”和备注；明确非医疗用途 |
| 多渠道商品命名不一致 | 搜索困难 | 以包装照片、品牌、肉源和质地共同识别 |
| 本地数据丢失或无法共享 | 长期使用受限 | MVP 先验证价值；后续评估微信云开发 |

## 11. 进入下一阶段的条件

满足以下条件后，再扩展云同步、识别准确率和趋势能力：

- 用户自然产生同款多次反馈，而不是只建档一次；
- 补货清单真实参与了购买决策；
- 反馈动作在实际喂食场景中足够轻；
- 用户能理解各状态，不需要反复解释；
- 至少有一部分用户愿意持续使用一个完整补货周期。

多猫不属于当前阶段范围；只有后续出现明确、持续的多猫反馈归属需求时，才重新评估。
